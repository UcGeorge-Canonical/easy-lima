# Provisioning, preset composition and replay evidence

**Status:** Internal design resolution for ELD-09 and ELD-14, selected on 2026-11-19. Normative for the planned implementation; not executed or independently re-reviewed. [The design](design_draft.md) retains the architecture and accepted update policy.

## Environment and version policy

The base is Ubuntu 24.04 LTS on the native guest architecture. Its qualified image must already supply systemd, Python 3, a POSIX shell, sudo and SSH so the controlled runner can be installed without an untracked bootstrap package transaction. Base setup installs the approved Git/OpenSSH client/CA/curl/build-essential/Python-venv/jq/rsync/archive package set. Development adds snapd, LXD `5.21/stable` and Juju `3/stable`. Docker is independent and can combine with development. Base always precedes optional presets; configuration list order does not change this dependency order.

The base package roots are `git`, `openssh-client`, `ca-certificates`, `curl`, `build-essential`, `python3`, `python3-venv`, `jq`, `rsync`, `tar`, `gzip`, `bzip2`, `xz-utils`, `unzip` and `zip`. Development apt roots are `snapd`, `apparmor`, `apparmor-utils` and `squashfs-tools`. Their dependency closures are frozen by the resolution stages, not inferred during a retry. A release catalog may not silently add another package root without an explicit environment revision.

Each release's disabled-until-qualified catalog entry contains image/assets and hashes, script/runner versions, package source/selection policy, exact Docker package versions for each architecture, snap IDs/revisions/assertion provenance, channels, and allocation bounds. Resolve those publisher values during release qualification; do not invent them in this draft. An enabled entry with missing values is invalid. Record actual installed versions and revisions separately. Start, retry and binary update do not resolve newer release inputs.

Base Ubuntu package candidates may be selected from the image's approved Ubuntu repositories during the explicit setup operation. A separate resolution stage freezes the complete proposed package transaction and repository evidence **before** installation. It includes dependency versions, archive digests/sizes and any upgrade/removal. Unexpected removals, source changes or changes outside the approved package/dependency closure block installation. Retrying uses that saved selection; unavailable archives cause a recoverable failure, not substitution with today's candidates. The first-create preview states this selection policy and package names; it does not pretend versions unresolved until boot are already known.

For a deliberate update, retain old and target environment revisions. An explicitly requested tool refresh selects the catalog/versions in that plan, even if a later easy-lima release appears before resume. Preset addition runs only its missing stages and prerequisites. Preset removal/uninstallation, distribution/architecture/image/driver replacement and disk resizing are outside v1 updates. User changes or unsupported package migrations require a separate plan; no arbitrary script rollback is attempted.

## Docker and development composition (ELD-09)

Use Docker's official Ubuntu stable apt repository, scoped by an owned source file and `Signed-By` keyring. The catalog pins the public repository-key digest/fingerprint and complete versions of `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin` and `docker-compose-plugin`. Verify repository signatures and package digests. Do not run a remote convenience script. Preexisting distro Docker/containerd packages or another repository/configuration are conflicts to diagnose, not authorization to remove them. Adopted environments keep their existing installation until an explicit supported update. [Docker Ubuntu installation](https://docs.docker.com/engine/install/ubuntu/).

Qualify Docker 29.x with the **iptables backend using Ubuntu's iptables-nft frontend**, not Docker's experimental native nftables backend. The exact release enters the catalog only after combined workload tests. Before first daemon start, write only the reviewed owned keys in `/etc/docker/daemon.json`: `firewall-backend="iptables"`, `iptables=true`, `ip6tables=true`, `ip-forward-no-drop=true`, and the plan's IPv4 bridge/address pools. No host network listener or Docker TCP API is enabled. Preserve unknown user keys with an expected-old check; conflicting values or command-line options prevent applying the preset.

Docker documents its forwarding policy and the no-drop option; LXD documents enabling forwarding before Docker to avoid its global DROP policy. This design selects both persistent early IPv4 forwarding and that explicit Docker option. It **does not reuse the prototype's service that repeatedly sets the global FORWARD policy to ACCEPT**. [Docker forwarding policy](https://docs.docker.com/engine/network/packet-filtering-firewalls/#docker-on-a-router), [LXD 5.21 coexistence guidance](https://canonical.com/lxd/docs/v5.21/howto/network_bridge_firewalld/#prevent-connectivity-issues-with-lxd-and-docker).

Owned networking consists of `/etc/sysctl.d/70-easy-lima-forwarding.conf` setting IPv4 forwarding for the selected development/Docker workload, the scoped Docker keys, and the LXD resources below. Apply the sysctl before starting either workload. Inspect existing filter policies and competing firewall managers; refuse a conflicting global DROP/custom ruleset rather than globally relaxing it or disabling another firewall. Leave Docker's own chains and LXD's firewall enabled. The qualified composition must work without an after-start broad ACCEPT workaround.

Install `/etc/systemd/system/docker.service.d/20-easy-lima.conf` **before package installation**, with `[Unit]` condition `ConditionPathExists=/var/lib/easy-lima/docker/configured`. Reload systemd and verify the effective condition before any package effect. The root-owned marker is private and bound to the frozen configuration/package digest in its receipt. This prevents package maintainer scripts from launching an unconfigured daemon. Publish that marker only after repository/packages/configuration/sysctl evidence is consistent, then enable/start Docker explicitly. The condition stays as an unchanged owned prerequisite; ordinary boot does not install/update packages or rewrite configuration. An explicit Docker update removes/reissues the marker through recorded steps and previews any restart. Never gate or restart an unrelated existing Docker service.

Hold only the five easy-lima-installed Docker packages against automatic apt upgrades. Explicit refresh uses the recorded target versions and restores the holds; no broad `apt upgrade` or global unattended-update change. Native Ubuntu security updates remain a separate OS policy and observation, not a claim of fully reproducible or immutable guests.

### LXD resources and addresses

On a fresh development preset create a directory-backed LXD pool `easy-lima`, bridge `elbr0`, and only the missing `root`/`eth0` devices on LXD's `default` profile. The root device uses `path=/`, `pool=easy-lima`; the NIC uses `network=elbr0`, `name=eth0`. Keep LXD's API on its local socket. An existing object/device is reusable only if ownership/provenance and all governed fields match; a same name is not ownership proof. Imported legacy resources retain their recorded names/settings instead of being renamed to these defaults.

The bridge uses the plan's explicit `/24`, gateway `.1`, IPv4 DHCP/NAT/firewall enabled and IPv6 disabled (`ipv6.address=none`). Choose an unused RFC1918 subnet from the finite candidate list in the catalog, in deterministic registration-ID order. Exclude observed non-default guest/host routes, other guest networks and planned Docker address pools. Retain the chosen addresses as immutable stage inputs and recheck before allocation; a conflict needs a new preview instead of an invisible change. There is no active subnet-probing heuristic. Two separate VMs may use the same internal subnet; neither receives an implicit host port mapping.

For Docker, the same allocator chooses non-overlapping bridge and default-address-pool ranges before daemon configuration. A lack of a valid candidate is a specific configuration conflict. Extra user-created networks remain user-managed and are checked for conflicts before subsequent owned changes. Ordinary startup never changes an address to make a check pass.

Append the development user to only the requested `lxd`/`docker` groups, preserving other memberships. Group access is privileged inside the trusted development VM and appears in the preview. Verify membership using a fresh SSH session. Do not bootstrap a Juju controller during VM setup.

After each managed LXD/Juju install or explicit refresh, set an indefinite **per-snap** hold and verify revision/channel/hold together. A targeted explicit refresh can proceed despite that hold; restore the hold afterward. Never change holds for unrelated or externally managed snaps. [Snap per-snap refresh behavior](https://snapcraft.io/docs/how-to-guides/manage-snaps/manage-updates/#if-snaps-are-specified).

## Stage executor and durable receipts

Use an embedded, versioned Python 3 `assets/guest/stage-runner.py` around the retained Bash preset scripts. Python is already a guest image/base requirement, not a new host runtime dependency. It supplies bounded JSON validation, atomic fsync/rename receipts, process observation and output draining without fragile shell-generated JSON. Scripts run as root or the explicitly recorded development UID as specified by the stage; secrets/profile private keys never enter their inputs.

The host copies the immutable runner/script/input bundle through pinned SSH into a private staging directory, checks guest hashes and records durable host dispatch intent. Start a named systemd transient service `el-<operation-id>-s<ordinal>-a<attempt>.service` with `Type=exec`, `Restart=no`, `KillMode=control-group`, `RemainAfterExit=yes`, null stdin and null systemd stdout/stderr. Pass fixed argv and paths; no shell interpolation of user fields. The runner executes the selected script from its complete local file, not a shell source stream that package commands could consume. Transient services give the job a lifetime independent of the SSH dispatcher; successful service launch is not stage success. [systemd transient services](https://www.freedesktop.org/software/systemd/man/latest/systemd-run.html), [systemd output routing](https://www.freedesktop.org/software/systemd/man/255/systemd.exec.html).

The runner continuously drains the script's stdout/stderr into a 64 KiB memory ring and an optional live Unix-socket subscriber; a slow/disconnected subscriber drops output with an explicit truncation count rather than blocking or killing the job. A separate bounded `stream` invocation relays it over SSH. The ring/socket live under `/run/easy-lima/<operation-id>/` with private permissions and vanish on reboot. No raw stream enters journald or a new guest log by default. Opt-in capture persists the stream on the host only; lost/disconnected output remains marked incomplete. Existing apt/snap/system logs are separate artifacts. Control receipts contain allowlisted classified results, never arbitrary stdout/error strings.

Persistent files are `/var/lib/easy-lima/operations/<operation-id>/<stage-id>/<attempt>/input.json` and `receipt.json`, root-owned with mode 0600; parent directories are 0700. Copy public diagnostic projections through the privileged read-only probe, not by weakening permissions. The receipt schema is:

| Field | Type/meaning |
| --- | --- |
| `schema_version` | Integer `1`. |
| `registration_id`, `operation_id`, `environment_revision_id` | Validated immutable IDs matching host intent. |
| `stage_id`, `stage_ordinal`, `attempt` | Catalog stage ID, positive integers; retries append attempts, never overwrite another one. |
| `input_sha256`, `script_sha256`, `runner_sha256` | Hashes of the exact admitted artifacts. |
| `boot_id`, `unit`, `invocation_id` | Guest boot ID, exact transient service name and systemd invocation ID. |
| `phase` | `prepared`, `may_have_effects`, `verified`, `failed` or `interrupted`. |
| `started_at`, `finished_at` | UTC timestamps; finish nullable. They order no authority. |
| `exit_code`, `result_code` | Nullable known numeric exit, allowlisted stable stage result; no raw error. |
| `substeps` | Ordered bounded records `{id, phase, before_digest, target_digest, after_digest, evidence}`; digest/evidence may be null when unknown. |
| `postconditions` | Bounded list of typed observations: owned-file hashes, package versions/status, snap change IDs/revisions/holds, LXD resource fields or service state. |
| `output_dropped_bytes` | Nonnegative count for the ephemeral output path. |

Limit each input/receipt to 256 KiB, reject unknown schema/stage fields and validate identifiers before deriving paths. The runner verifies the host bundle and takes an exclusive per-operation guest file lock before writing `prepared`. Before each mutating substep it durably writes `may_have_effects`, then dispatches. It writes `verified` only after all stage-specific postconditions pass. It never writes a success receipt from exit status alone. The host re-observes postconditions before advancing the environment's applied revision; guest receipts are evidence within the trusted-guest model, not a hostile-guest attestation.

A host disconnect/cancel does not cancel or duplicate the guest unit. A dead runner's child may still live in the unit cgroup; a free file lock is insufficient. Observe the exact unit/invocation, all remaining cgroup processes and snapd changes associated with the attempt. After reboot the transient unit can be absent while disk effects remain. Keep immutable attempts/receipts until host reconciliation and retain unresolved evidence. No startup hook resumes provisioning on reboot.

## Shipped stage catalogue (ELD-14)

Every ID below is immutable at version `v1`; a semantic change creates another stage version/script digest. Each stage receives the common bundle above plus the listed inputs. The order is dependency order; independent stages may be skipped when their exact target already has valid evidence, but v1 executes guest mutations sequentially for one VM.

| Stage ID | Prerequisites and frozen inputs | Ordered effects and completion evidence |
| --- | --- | --- |
| `env.inspect.v1` | Running same VM, pinned SSH, image/OS/UID expectations. | Read systemd/Python/OS/architecture, mount and capacity prerequisites. No persistent guest effect; mismatch blocks later stages. |
| `base.resolve.v1` | Inspect passed; approved Ubuntu source fingerprints/package names. | Refresh only approved apt indices; simulate complete transaction; record version/archive/digest closure durably for host acknowledgment. No package install. A saved valid selection is reused, not re-resolved on retry. |
| `base.install.v1` | Host-committed resolution artifact and enough guest capacity. | Install the exact saved archives/versions without removals or broad upgrades; verify dpkg configured state and each required package/tool. Partial dpkg work is not a new resolution request. |
| `base.runtime.v1` | Base tools present; development UID/home/workspace and target hashes. | Install only owned shell/runtime directories, signing-independent helper files and tmpfiles rules. Verify ownership/modes/hashes and `/workspace` source identity. Preserve existing user files/includes. |
| `dev.resolve.v1` | Verified base; requested development and approved Ubuntu sources/development package roots. | Apply the same bounded resolution protocol as base.resolve for the development closure; retain its separate immutable artifact and obtain host acknowledgment before any development package installation. |
| `dev.snapd.v1` | Base; requested development; host-committed dev.resolve transaction for snapd/AppArmor dependencies. | Install those packages, enable required snapd/AppArmor services, wait for seeded state with bounded observation. Verify configured packages, services and snapd capability for per-snap holds. |
| `dev.lxd.v1` | Snapd ready; catalog LXD ID/revision/channel/assertions. | Install/target-refresh LXD, retain snapd change ID, wait for that change, set only its hold, verify exact revision/channel/hold and local API readiness. |
| `dev.juju.v1` | Snapd ready; catalog Juju ID/revision/channel/assertions and classic-confinement selection. | Install/target-refresh Juju with the declared confinement, retain change ID, hold and verify revision/channel/hold and executable. No controller creation. |
| `dev.pool.v1` | LXD ready; owned pool name/driver and absence/old digest. | Create the directory-backed pool if absent under admitted intent; verify name, driver and ownership evidence. Never replace another pool or destroy volumes. |
| `dev.bridge.v1` | LXD ready; pinned bridge/CIDR and expected-old network evidence. | Recheck address conflicts, apply owned IPv4 forwarding prerequisite, create the bridge and verify every governed IP/NAT/DHCP/firewall field. Existing differing network is a conflict. |
| `dev.profile.v1` | Pool/bridge verified; expected-old default-profile devices. | Add missing owned root/NIC devices one at a time with receipts, then verify both references and unchanged other devices. Never replace user devices. |
| `docker.source.v1` | Base; explicit Docker selection and absence of conflicting packages/sources. | Write owned scoped apt source/keyring and startup-gating drop-in, verify hashes/signature trust and effective gate. No daemon start or package removal. |
| `docker.config.v1` | Source/gate ready; selected addresses/backend and expected-old config/sysctl. | Apply scoped Docker JSON and IPv4 forwarding settings before any daemon start; verify effective config, routes/filter prerequisites and untouched user fields. In combined mode the LXD bridge must already be verified. |
| `docker.install.v1` | Verified config/gate; catalog exact complete package closure. | Install exact packages, verify all configured versions, set their individual apt holds. Verify no unapproved daemon startup occurred; keep gate closed until ready. |
| `docker.service.v1` | Config/package/hold postconditions true. | Publish owned ready marker, enable/start or explicitly previewed restart, verify daemon version/backend, effective config, socket-only API and network policies. No rule that rewrites global FORWARD policy. |
| `access.groups.v1` | Selected tools ready; UID and intended added memberships. | Append only requested groups, then verify using a fresh SSH session. No profile-agent interaction. |
| `identity.bundle.v1` | Optional bound profile and verified base/runtime; frozen public identity target. | Delegate to the profile/connection contract's owned bundle, trust and forwarding checks. Skip with a distinct reason for profile-free VMs; no separate guest private-key setup. |
| `env.verify.v1` | Required stages observed complete. | Read service/configuration/version/mount results and actual usage; run only explicitly planned disposable setup probes. Record complete environment evidence and separate identity/provider results. Read-only doctor uses its own no-write checks instead. |

`dev.snapd` package selection uses the same resolve/install evidence contract as base, with a separate immutable resolution artifact. Docker's complete closure is resolved from the catalog's exact top-level versions and approved repository before its install stage. If dependency resolution adds unapproved operations, stop with the transaction diff; never install just to discover whether it works.

The combined dependency order is base → snapd/LXD/Juju → LXD pool/bridge/profile → Docker source/config/install/service → groups → optional identity → verification. Docker-only skips development stages. Development-only skips Docker stages. Updates use the graph induced by explicitly changed targets and unsatisfied prerequisites, preserving previously applied resource/identity bindings. An LXD install can be complete while pool/bridge setup remains pending; these are separate stage records.

## Stage-specific reconciliation

All categories below require matching registration, input and code hashes. `active` takes precedence while the exact unit/cgroup/snap change is running, even if a target is already visible. No evidence from a different boot or dispatch is silently attached to the current attempt.

| Stage class | Satisfied | Not applied / permitted replay | Partial or unknown |
| --- | --- | --- | --- |
| Read/resolve | Valid saved selection and host acknowledgment, or exact read postconditions. | No saved selection and no active resolver; the original source/policy still matches. Index refresh can repeat before a selection is committed. | Saved selection digest disagrees, source changed or incomplete transaction closure: block; never silently select newer versions. |
| apt install | All exact targets configured; actual transaction stays within approved closure and holds as required. | Prepared-before-effect receipt, no active unit/package process, unchanged before-state and no package effects. | Mixed configured/unpacked states or locks/process ambiguity: block for explicit package repair/reconciliation. Do not blindly run dpkg repair or reinstall everything. |
| Snap install/refresh/hold | Recorded target revision/channel/hold, completed matching change and tool readiness. | No active change, unchanged before-state and evidence that dispatch did not occur. | Known target installed with only hold missing can complete that still-approved owned hold substep after recheck. In-flight changes are observed; unknown/reverted/different revisions block. |
| Owned files/sysctl/gate | Each target hash/value and intended service gate matches. | Observed exact old/absent target, no active writer and recorded before-state matches: retry that substep only. | Exact target already written advances verification; any third value or unexpected live sysctl is a conflict. Do not overwrite user edits. |
| LXD pool/bridge/profile | Owned object/devices match the complete intended fields and reference graph. | Exact expected absence/old value, no active job and admitted ownership allows creating the missing object/device. | Already-created exact object is verified; continue only missing approved devices. A different value or unowned same-name object blocks. Never delete/recreate a pool or network as rollback. |
| Docker service | Matching daemon version/config/backend, gate, holds and required network results. | Proven inactive/stopped same service after exact prerequisites; start is still in the approved plan. | An active mismatched daemon or ambiguous restart remains blocked/unknown. No restart simply to inspect it; ordinary VM start cannot refresh the preset. |
| Groups | Intended added memberships plus a fresh session match. | Exact old membership and no active mutation permits the missing append. | User/member conflicts are reported; never replace the entire supplementary-group list. |
| Identity | Applied/pending profile and VM trust generations meet their own contracts. | Only the recorded identity continuation can proceed. | Follow PROFILE_TRANSITIONS/ADOPTED_AGENTS; no alternate key or implicit lock clearing. |
| Setup probes | Successful matching probe receipt plus observed cleanup. | Read-only portion can repeat; disposable probe replay requires known cleanup of the exact prior test resource. | Retain leaked/unknown test-resource IDs for explicit cleanup; do not delete arbitrary similarly named resources. |

After a reboot, lost transient-unit evidence is **not** evidence of no effect. Verify durable target state; otherwise keep unknown. A receipt alone cannot override a conflicting live postcondition. The host records the reconciliation classification and new dispatch ordinal before continuing an approved missing substep. Partial repair that changes the original effects requires a new preview; arbitrary script rollback remains excluded.

## Native-template stages

Resolve supported native YAML/base dependencies into immutable local inputs before creation. `system` and `user` scripts that are explicitly one-time setup may become `native.<sha256>.v1` stages in original order, with the original UID, full script bytes and declared environment retained privately. Remove their native automatic execution only in the **prepared creation template** after previewing the equivalent explicit stage mapping. A retained script containing unknown secrets is not printed/logged merely because its artifact must be retained.

Recurring boot/always modes, host-side provisioners, dynamic downloads/includes and semantics that cannot be preserved are rejected before create/adoption/update. No arbitrary script is treated as idempotent. After a verified receipt plus declared postconditions, it can count complete; interruption after `may_have_effects` without a trustworthy completion predicate stays unknown and requires explicit recovery. V1 adds no custom rollback language or heuristic replay. Adopted completed legacy provisioning remains historical evidence; it is never automatically converted into fresh current-preset stages.

## Planned files and qualification

Keep the host environment coordinator, stage catalog and reconciliation in `internal/environment`; add `stages.go`, `stages_test.go`. Use `assets/presets/base.sh`, `development.sh`, `docker.sh` as versioned effect implementations invoked by stage/substep ID; replace the planned generic shell runner with `assets/guest/stage-runner.py`. Add `testsupport/guest/test_stage_runner.py` and typed scenario fixtures `testdata/provisioning/stages-v1.json` and `testdata/provisioning/reconciliation-v1.json`. The release catalog carries every stage/script hash and qualification result. No host Python runtime is introduced.

Qualification requires base-only, development-only, Docker-only and combined environments on every advertised host/architecture. Verify Docker build/run/DNS/egress and Compose, a real LXD container's storage/DNS/egress, and disposable Juju LXD bootstrap/deploy/cleanup. Repeat after Docker restart, LXD restart and VM reboot; check explicit host-port exposure separately. A conflicting firewall remains an actionable conflict, not an automatic policy reset.

Fault cases include disconnect while a job continues, killed runner with surviving cgroup work, reboot after package installation, interruption between pool/bridge/device creation, snap install before hold, Docker gating/config/hold/start boundaries, changed script/input digests and user-edited settings. Recovery must identify the exact completed stage and continue only justified substeps. Verify raw-output opt-in, bounded memory/draining, receipt durability and no hidden every-boot provisioning. These are required tests, not results already obtained.
